Generate a TLS key log (SSLKEYLOGFILE)

Chrome, Edge, Brave and Firefox can write their TLS session keys to a file when the SSLKEYLOGFILE environment variable is set. That file lets this tool (and Wireshark) decrypt TLS 1.3 — revealing the real certificate and the inner HTTP behind an SWG/proxy. Set the variable, launch the browser from the same shell, reproduce the issue, then upload the file.

  1. Close the browser completely. Quit every window; confirm no chrome.exe / msedge.exe is left running (Task Manager → Details). A background process will ignore the variable.
  2. Open PowerShell and set the variable for this session: 
    $env:SSLKEYLOGFILE="$env:USERPROFILE\Downloads\sslkeys.log"
  3. Launch the browser from that same PowerShell window (so it inherits the variable): 
    # Chrome
& "C:\Program Files\Google\Chrome\Application\chrome.exe"
# Edge
& "C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe"
  4. Reproduce the problem in that browser (visit the site, trigger the error).
  5. Capture in Wireshark at the same time if you need the PCAP too. Then upload Downloads\sslkeys.log here alongside the capture.

Make it persistent (optional): 

[Environment]::SetEnvironmentVariable("SSLKEYLOGFILE","$env:USERPROFILE\Downloads\sslkeys.log","User")
Then sign out and back in so all apps pick it up.

  1. Quit the browser completely (Cmd+Q — not just the window).
  2. Open Terminal and export the variable: 
    export SSLKEYLOGFILE="$HOME/Downloads/sslkeys.log"
  3. Launch the browser binary directly from that Terminal (using open may not pass the variable, so call the executable): 
    # Chrome
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome"
# Edge
"/Applications/Microsoft Edge.app/Contents/MacOS/Microsoft Edge"
# Firefox
"/Applications/Firefox.app/Contents/MacOS/firefox"
  4. Reproduce the problem in that browser.
  5. Upload ~/Downloads/sslkeys.log here (with the PCAP if you captured one).

Make it persistent (optional): add the export line to ~/.zshrc, then source ~/.zshrc and relaunch the browser from a new Terminal.

  1. Close the browser completely (quit all windows and background processes).
  2. Open a terminal and export the variable: 
    export SSLKEYLOGFILE="$HOME/sslkeys.log"
  3. Launch the browser from that same terminal: 
    google-chrome     # or: chromium
microsoft-edge    # Edge
firefox           # Firefox
  4. Reproduce the problem in that browser.
  5. Upload ~/sslkeys.log here (with the PCAP if you captured one).

Make it persistent (optional): add the export line to ~/.bashrc (or ~/.profile), then open a new terminal and relaunch the browser.

The key log can decrypt everything that browser did while it was set (banking, email, work apps). Treat it as a secret, keep it local, and delete it after analysis. Unset the variable / relaunch normally when you are done.

Network-analysis guide

Short, plain-language explanations of what this tool shows you. No prior packet-capture experience needed.
🔗 What is a “flow”?

A flow is a single conversation between two endpoints — one client (your machine) talking to one server, over one port. Wireshark calls it a TCP/UDP stream.

Every row in Flows is one flow. Expanding a row shows its Connection flow diagram: each arrow is a packet, blue = client→server, green = server→client, top to bottom in time.

🤝 The TLS handshake

Before any encrypted data, client and server negotiate in the clear:

  • SYN / SYN-ACK — TCP opens the connection.
  • ClientHello — client offers ciphers, TLS version & the SNI (the hostname it wants).
  • ServerHello + Certificate — server picks the cipher and presents its certificate.
  • Application Data — everything after this is encrypted.

The tool reads this metadata to tell whether traffic was decrypted, passed through, or fully hidden.

🛡️ Decryption posture (the badges)

How the proxy/SWG treated each TLS flow:

Decrypted — the certificate was re-signed by your SWG’s CA. The proxy opened, inspected and re-encrypted the traffic.
Pass-through — a real public CA certificate. The proxy let it pass uninspected.
TLS 1.3 — the certificate itself is encrypted, so it can’t be read from the capture alone.
Tunnel — an opaque CONNECT tunnel; only endpoints are visible.

🏷️ SNI, certificates & CA re-signing

SNI (Server Name Indication) is the hostname the client asks for inside the ClientHello — it’s how the tool names a flow even when traffic is encrypted.

A certificate proves the server’s identity and is signed by a CA (Certificate Authority). When a SWG decrypts, it swaps the real certificate for one it signs with its own CA — that swap is exactly what the Decrypted badge detects.

🧬 JA3 / JA3S fingerprints

JA3 is a fingerprint of the client’s ClientHello; JA3S fingerprints the server’s ServerHello. They work even on TLS 1.3 because they use clear-text handshake fields.

Many different destinations sharing one JA3S often means a single TLS terminator — i.e. a proxy is decrypting everything behind it.

🌐 DNS: resolution & block pages

DNS turns a name (teams.microsoft.com) into an IP. A name often points to a CNAME chain before landing on an address — the DNS tab and each flow show that chain plus which resolver answered.

If Secure Access blocks a domain, DNS may return a block-page IP instead of the real one — the tool flags those so a “failure” isn’t mistaken for a network fault.

⚡ QUIC / HTTP-3

QUIC is HTTP-3 over UDP/443. Secure Access does not intercept QUIC — it passes uninspected. That’s why QUIC gets its own channel color: if you expect inspection, the client should be steered to fall back to TCP/TLS.

🏢 Proxy / SWG / SASE / Secure Access

A SWG (Secure Web Gateway) sits between the user and the internet to enforce policy. SASE delivers that from the cloud. Cisco Secure Access is Cisco’s SASE — it can decrypt, inspect and block traffic. This tool’s job is to show, from a capture, what it actually did.

📊 Reading severity & the sequence diagram

Severity highlights flows worth attention (resets, TLS alerts, failed handshakes). “Show only problems” filters to those.

In a flow’s Connection flow diagram, each arrow’s bright end is where the packet arrives; the faint end is where it left. Red arrows mark anomalies like RST or TLS alerts.
